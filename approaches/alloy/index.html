Alloy

Explore structures and counterexamples described by relational constraints.

Advanced · 3 drills · Reviewed 2026-10-24

See an examplePractise

What it helps you do

Test whether an intended property actually follows from a set of modeled relationships and constraints.

Starting knowledge: Comfort with sets, relations, and logical constraints helps.

  • Define entities and relations precisely.
  • Separate facts that constrain every instance from assertions you want to check.
  • State the analysis scope and inspect any counterexample.

The problem it came from

Daniel Jackson and collaborators developed Alloy in MIT’s Software Design Group. Its language draws on relational logic and related formal-modeling traditions.

The Alloy Analyzer searches for structures satisfying a model and counterexamples to assertions within a configured scope. The current language also supports temporal modeling; this entry uses a small structural example.

Work through an example

STARTING POINT
Each registration has one participant and one workshop, so duplicate registrations must be impossible.
APPLYING THE APPROACH
sig Participant {}
sig Workshop {}
sig Registration {
  participant: one Participant,
  workshop: one Workshop
}
assert NoDuplicatePair {
  all disj a, b: Registration |
    a.participant != b.participant or a.workshop != b.workshop
}
check NoDuplicatePair for 3
  • Exactly one participant per registration does not imply one registration per participant/workshop pair.
  • The assertion is a property to investigate, not an added fact.
  • This source example has not been executed by this website; run it in the Analyzer to inspect its result.

Where it helps. Where it stops.

Use it when

  • A data or access model has interacting relationships.
  • A claim about uniqueness, ownership, or reachability needs a concrete counterexample search.

Potential benefits

  • Small generated structures can make a design flaw tangible.
  • An assertion separates a desired property from rules that actually imply it.

Limits and common mistakes

  • A bounded search without a counterexample is not an unrestricted proof.
  • Putting the desired outcome into a fact can make an assertion pass without testing the intended design.

DRILL 02 Not attempted

Choose one answer

Hint

Separate assumptions from claims.

Explained answer

Best answer for this case: It would assume the property being investigated

A fact restricts possible models. Assuming the desired conclusion can remove the counterexamples you intended to discover.

DRILL 03 Not attempted

Explain what a counterexample with two registrations for one pair would teach you.

Hint

What exactly does the structure demonstrate?

Explained answer & self-review rubric

The existing constraints allow duplicates even though the assertion forbids them. Add or redesign the intended uniqueness constraint, then check whether the implementation enforces it. The counterexample concerns the model, not automatically the deployed database.

  • Interpret the violated assertion
  • Identify the missing constraint
  • Separate model and implementation
