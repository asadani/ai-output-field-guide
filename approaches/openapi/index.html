OpenAPI

Describe an HTTP API’s operations, inputs, responses, and security requirements.

Intermediate · 3 drills · Reviewed 2026-10-24

See an examplePractise

What it helps you do

Give people and tools a shared interface description without requiring them to infer the API from implementation code.

Starting knowledge: Know the basics of HTTP requests, responses, and status codes.

  • Describe paths and operations from the consumer’s perspective.
  • Specify requests and relevant success and error responses.
  • Keep authentication descriptions distinct from actual authorization enforcement.

The problem it came from

The OpenAPI Specification grew from the Swagger ecosystem and is maintained through the OpenAPI Initiative. It provides a language-independent description of HTTP interfaces.

This entry references OpenAPI 3.1.0, published in 2021, as a specific teaching baseline. It does not claim that this is the newest release.

Work through an example

STARTING POINT
Send a registration object to the service and handle whatever comes back.
APPLYING THE APPROACH
openapi: 3.1.0
info:
  title: Workshop API
  version: 1.0.0
paths:
  /registrations:
    post:
      responses:
        "201":
          description: New registration created
        "400":
          description: Registration input is invalid

# Minimal teaching document; request schemas and other outcomes
# must be added for a real registration contract.
  • The example names the HTTP operation.
  • The response statuses distinguish creation from invalid input.
  • The comment explicitly identifies what this minimal document leaves out.

Where it helps. Where it stops.

Use it when

  • Designing or reviewing an HTTP interface.
  • A payload schema exists but clients cannot tell where to send it or how failures are represented.

Potential benefits

  • A shared contract supports documentation, tooling, and implementation review.
  • Explicit failure responses expose missing behavior early.

Limits and common mistakes

  • A specification can disagree with the running service.
  • Security declarations describe requirements; they do not install enforcement.

DRILL 03 Not attempted

What should a registration API describe when the input is missing required information?

Hint

What does a client need to recover?

Explained answer & self-review rubric

Describe the relevant client-error response and its payload, including how the missing information is identified. Agree the status and error semantics instead of assuming all failures return the same success shape.

  • Include an error response
  • Describe its body
  • Avoid inventing unapproved semantics
